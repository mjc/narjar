# NARJ-30 continuation decision

Decision: **continue Narjar; do not adopt bincache**.

This decision applies the predeclared gate to Narjar commit `905ca46d3433a6e23ee06aaccf4c1c2810b00ede` and bincache commit `556a9c8f97a3c994a9de85f567a2ef16ce6513ab`. The matched run used Tina, Linux 6.18.44, a Ryzen 9 5950X in the performance governor, ZFS, Nix 2.31.5, Rust 1.85.1, seed 29030, one warm-up, and 15 measured repetitions.

## Gate

Narjar had to remain protocol- and trust-correct and be materially smaller or simpler in at least two of startup, RSS, closure, operational state, and upload CPU.

| Premise | Result | Evidence |
| --- | --- | --- |
| Startup | No win | Narjar is faster at 0 paths (2.813 ms vs 24.453 ms median) and 100 paths (7.340 ms vs 24.362 ms), but slower at 1,000 paths (50.175 ms vs 22.586 ms) and 10,000 paths (478.590 ms vs 28.924 ms). |
| Settled RSS | Win | At 10,000 paths Narjar uses 2,096 KiB vs 17,732 KiB median, 88.2% less. At 0 paths it uses 2,060 KiB vs 11,548 KiB. |
| Runtime closure | Win | The dynamic closure is 44,444,720 bytes vs 51,957,664 bytes, 14.5% smaller. The static Narjar closure is 1,541,800 bytes, 97.0% smaller than bincache. |
| Operational state | Win | Narjar reconciles automatically on restart in one operator step; bincache requires stop, explicit reconcile, and restart. Narjar's measured restart/reconcile wall time is slower (484.052 ms vs 69.249 ms), so this is a simplicity win, not a latency win. |
| Upload CPU | Win | Median server CPU for 16 MiB uploads is 20 ms vs 30 ms. For the 1 GiB streaming upload it is 1,480 ms vs 2,070 ms, 28.5% less. |

Narjar wins four of five premises, exceeding the required two.

## Correctness and bounds

Both candidates served GET and HEAD with status 200, byte ranges with status 206, and missing paths with status 404. Both substituted an input-addressed derivation into a fresh Nix store with the matching public key and rejected the same operation with an unrelated key.

Duplicate uploads added zero stored bytes for both candidates. Concurrent duplicate uploads completed for both. Interrupted uploads remained invisible before and after restart. A real 64 MiB upload into a private 8 MiB tmpfs failed for both candidates while each server stayed alive; the path remained 404 after failure and restart.

Narjar's peak RSS stayed near 2.2 MiB for both the 100 MiB and 1 GiB streaming uploads. Bincache used 27,248 KiB and 22,860 KiB respectively. Narjar stored the 1 GiB payload with 652 bytes of logical overhead versus 24,697 bytes for bincache.

Read performance is not a Narjar win: bincache has lower median cold and warm single-reader latency, while wider-reader results are mixed. This does not change the continuation gate, but it remains a performance constraint.

The principal follow-up risk is startup scaling. Narjar's 10,000-path startup median is 16.5 times bincache's. Continuation is authorized because the gate is satisfied elsewhere, not because startup scaling is acceptable.

- `enospc.json`, `substitution.json`, and `recovery-operations.json`: failure, trust, and operator-path evidence.

Large upload payloads are deterministic incompressible data generated by the committed runner from seed 29030; their labels and byte sizes are retained in the raw samples rather than committing multi-gigabyte payload files.
